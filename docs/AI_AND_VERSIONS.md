# Проектная записка: ИИ-агент и контроль версий

Статус: **план, ничего из этого ещё не написано**. Документ фиксирует замысел, границы и порядок работ, чтобы по каждому
этапу можно было сказать «готово» или «не готово». Принципы проекта действуют полностью: [PRINCIPLES.md](PRINCIPLES.md)
(«Не убий», стабильность на любом ПК, открытость, проверяемость). Всё, что здесь названо «гипотезой», нужно проверить
экспериментом на живом КОМПАС до начала работ.

## 1. Что хотим

1. **ИИ-агент рядом с КОМПАС** (как в VS Code): подключить любую модель, попросить «сделай деталь…», «измени диаметр…»,
   видеть, что именно он делает, принять или отклонить.
2. **Контроль версий моделей** (как Source Control в VS Code): видеть, что изменилось, фиксировать состояния, возвращаться.
3. Работать это должно **на любом ПК без установки чего-либо** (Python, git и т.п.), не ломая файлы и КОМПАС.

## 2. Общий фундамент: «деталь как код»

Двоичный файл `.m3d` нельзя сравнить построчно и нельзя осмысленно править языковой моделью. Поэтому оба замысла опираются
на одну идею: у детали есть **текстовое описание построения (рецепт)**, из которого её можно построить заново.

- **Формат** (набросок): файл `*.mkga.json` с разделами `params` (именованные размеры), `ops` (операции в порядке
  построения: эскиз из примитивов, выдавливание, вырез, вращение, условное изображение резьбы), `props` (наименование, раздел
  спецификации, материал) и `expect` (что должно получиться: габариты, объём с допуском). Операции это ровно то, что уже
  умеет `mkga.core.model3d` и что проверено на живом КОМПАС.
- **Каталог комплектующих уже работает по этому принципу**: стандарт это таблица размеров плюс форма (код), а не файл детали.
  Рецепт обобщает «форму» до описания, которое может написать ИИ или человек.
- **Проверяемость**: рецепт всегда строится сначала в скрытом документе; проверяются успешность каждой операции, объём > 0,
  совпадение с `expect`. Если построение не удалось, на диск ничего не попадает.
- **Чужие детали** (нарисованные вручную): рецепта у них нет. Гипотеза: часть дерева построения можно прочитать через API
  (операции, эскизы, переменные). Это отдельное исследование (этап 7); до него такие детали версионируются как файлы
  со сводкой свойств, а ИИ может только читать сводку и создавать новые детали.

## 3. Контроль версий

### Что хранится

Проект это папка с вашими деталями; внутри скрытая `.mkga/` с хранилищем состояний. Состояние («фиксация») это набор
файлов (по хешу SHA-256), сообщение, время и родитель. Хранятся: сами файлы КОМПАС, рецепты, при наличии сводки.

**Решение к обсуждению: своё хранилище или git.** Рекомендация: **своё простое хранилище** (содержимое по хешу, без
зависимостей, работает у любого пользователя), плюс экспорт истории в настоящий git для тех, кому он нужен. Использовать
git «если он установлен» нельзя как основу: поведение на машинах без него разное. Плата за своё: слияния и ветки сначала
нет (для двоичных файлов их всё равно нет).

### Что показывается в «изменениях»

| Уровень | Для чего | Как получается | Статус знаний |
|---|---|---|---|
| Список файлов | добавлен, изменён, удалён | сравнение хешей | тривиально |
| Сводка детали | масса, объём, габариты, свойства (наименование, раздел спецификации), переменные | чтение через API в скрытом документе | масса, объём и свойства уже читаются; габариты и переменные гипотеза |
| Рецепт | построчные различия | текст | тривиально |
| Картинка | было/стало, изометрия | снимок модели через API | гипотеза: экспорт растра документа |
| Сборка | состав (позиции спецификации) | чтение спецификации | спецификация сборки читается (проверено в каталоге) |

Честное ограничение: для чужих деталей без рецепта различия видны на уровне **сводки и картинки**, а не отдельных операций.

### Операции и интерфейс

«Зафиксировать» (с сообщением), «История», «Сравнить», «Вернуть» (файл возвращается из хранилища через сессию отката:
прежняя версия уходит в корзину и в журнал, как все изменения в MKGA). Окно «Версии» устроено как панель Source Control
в VS Code: слева группы изменений, внизу поле сообщения и кнопка, справа различия выбранного файла. Автоснимок делается
перед каждым действием ИИ или мода, которое меняет файл (сейчас такой снимок уже есть у всех записей MKGA).

Не планируется: слияние двоичных файлов, блокировки, облачное хранение (можно положить папку проекта в любой облачный диск
или git самим).

## 4. ИИ-агент

### Слой 1: MCP-сервер (сначала)

**MCP** (Model Context Protocol) это открытый протокол, по которому ИИ-приложения (Claude, VS Code, Cursor и другие)
вызывают «инструменты». MKGA выставляет свои возможности как инструменты, и **любой** MCP-клиент получает доступ к КОМПАС
без нашего интерфейса. Сервер на чистой стандартной библиотеке (JSON-RPC по stdio), запускается из того же `MKGA.exe`
(`MKGA.exe mcp`), зависимостей нет. Уже известно, что в сообществе есть чужие MCP-сервера для КОМПАС; наш отличается тем, что
**не выполняет произвольный код** и пишет только через сессию отката.

Инструменты (набросок):

- чтение: состояние КОМПАС, открытые документы, сводка детали, список стандартов каталога, предпросмотр (картинка);
- создание: деталь из стандарта (уже умеем), деталь из рецепта в скрытом документе с предпросмотром;
- применение: сохранить результат в файл (только после подтверждения человеком в окне MKGA), вернуть предыдущее состояние.

### Слой 2: чат в хабе

Окно с чатом: выбор провайдера (Anthropic, OpenAI-совместимые, локальные Ollama или LM Studio), ключ хранится в Диспетчере
учётных данных Windows, а не в файлах. Цикл «модель вызывает инструмент, мы показываем вызов и результат». Для правки
детали «как код» модель меняет рецепт, мы показываем различия рецепта и картинку «было/стало», пользователь принимает или
отклоняет; принятое попадает в версию.

### Безопасность (обязательные правила)

1. **Нет произвольного кода.** ИИ вызывает узкий список инструментов; прямой доступ к COM и `exec` не выдаётся.
2. **Запись только через сессию отката**, по умолчанию в новый файл или копию; перезапись открытого документа пользователя
   только с отдельным подтверждением.
3. **Человек в контуре:** сохранение на диск подтверждается в окне MKGA, не самим ИИ и не текстом из документа.
4. **Данные документа это данные, а не инструкции** (имена, свойства, комментарии могут содержать попытку подсказать модели
   команду). Результаты инструментов маркируются как данные; текст из документов не может расширять права.
5. **Журнал действий ИИ** (что вызвано, с какими параметрами) и лимиты (число операций, время, размер).
6. **Приватность:** перед первым запуском показывается, что уходит провайдеру (описания деталей, картинки, сводки), ничего
   не отправляется без согласия; локальные модели позволяют работать без сети. Ключи не попадают в репозиторий и в журналы.
7. Режим «только чтение» для тех, кто не хочет, чтобы ИИ что-либо создавал.

## 5. «Прямо в интерфейсе КОМПАС»

| Вариант | Что это | Оценка |
|---|---|---|
| **A. Окно рядом** (рекомендуется) | запускается из меню КОМПАС (уже есть), по желанию прикрепляется к краю окна КОМПАС и следует за ним (положение окна читается средствами Windows) | без новых зависимостей, КОМПАС не затрагивается; проверяемо |
| B. Настоящая встроенная панель | библиотека-приложение (.rtw или .NET) внутри процесса КОМПАС | нужен компилятор и поставка DLL; **ошибка в ней роняет КОМПАС**, что противоречит принципу «Не убий». Только после этапов 1-5 и отдельной оценки риска |

## 6. Этапы и критерии готовности

| № | Этап | Готово, когда |
|---|---|---|
| 0 | Выпуск хаба и мода (см. [RELEASING.md](RELEASING.md)) | любой человек скачал, поставил, создал деталь |
| 1 | **Деталь как код**: формат рецепта, исполнитель, проверки, 5 и более деталей | рецепт строит деталь на живом КОМПАС, объём и габариты сходятся, повторное построение даёт тот же результат |
| 2 | **Версии, основа**: хранилище, зафиксировать, история, вернуть (CLI и окно) | файл возвращается по байтам, откат вернётся; сводка детали читается и сравнивается |
| 3 | **Версии, различия**: картинка «было/стало», различия рецептов, окно как Source Control | на двух версиях одной детали видно, что именно изменилось |
| 4 | **MCP-сервер**: чтение, создание из стандартов, затем из рецепта с предпросмотром | автотест протокола; ручная проверка подключением Claude Desktop и VS Code |
| 5 | **Чат в хабе**: провайдеры, хранение ключей, показ действий | сквозной сценарий «попросил, увидел различия, принял» на облачной и на локальной модели |
| 6 | **Окно рядом с КОМПАС**: прикрепление, запуск из меню | окно следует за КОМПАС и не влияет на его стабильность |
| 7 | Расширения: чтение дерева построения чужих деталей, сборки, экспорт в git, ветки для рецептов | по результатам исследования |

## 7. Что нужно выяснить экспериментом до этапов

1. Можно ли через API7 прочитать дерево построения детали (операции, эскизы, размеры) и в каком объёме.
2. Можно ли получить картинку модели через API (экспорт растра документа) без показа окна.
3. Можно ли надёжно читать габариты и переменные детали.
4. Есть ли события или способ узнать о сохранении документа (для автоснимков).
5. Насколько точно ИИ строит несложные детали по рецепту (набор из 10 заданий и подсчёт доли удачных).

## 8. Решения, которые нужны от владельца проекта

1. Хранилище версий: **своё** (рекомендация) или git.
2. Какие провайдеры ИИ поддержать первыми (облачные, локальные или оба сразу).
3. «Встроенность»: окно рядом (рекомендация) или настоящая панель внутри КОМПАС после оценки риска.
4. Порядок: после выпуска сначала рецепты и версии (этапы 1-3), затем ИИ (4-5), или MCP раньше как самый быстрый способ
   подключить ИИ (рекомендация: этап 1, затем 4, затем 2-3, затем 5).
